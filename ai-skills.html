1. When you do not know how to implement a feature

Example: your solver already computes an answer. You do not know how to let a user select a previous result and restore its inputs.

  1. Describe what exists. Identify the actual files/classes, current behavior, JDK 21/JavaFX setup, and the one missing behavior. Use your real names in place of the illustrative names below.
  2. Ask for a small explanation first. “Explain how selection events could connect our history list to the selected result. What should the session model own? Show a short sketch; do not edit yet.”
  3. Predict the behavior. Solve A, solve B, select A: A’s inputs and answer should return. Select nothing: no crash and no invented result. Write these expectations before accepting code.
  4. Try one limited change. On a feature branch, ask the agent to connect selection to the existing model and view. Name allowed files and preserve agreed public methods. Inspect the diff before proceeding.
  5. Read and explain. Identify the event, model object, state change, and display update. Ask about unfamiliar lines, then explain them yourself to a teammate.
  6. Verify independently. Run your expected cases. Also solve C after selecting A: no old result should leak into the new calculation. If something fails, report the exact steps and expected/actual behavior.
  7. Review, share, and cite. Keep the useful change, correct or reject the rest, and open a reviewed PR. Record the tool, assistance, and what you learned in your AI Learning Log.
A task prompt you can adapt
Goal: selecting a previous result restores its inputs and answer.
Context: Java 21 / JavaFX; our existing Maven project already runs.
Relevant files: [actual view file], [session model], [result class].
Current behavior: solving works; selecting history does nothing.
Explain the event-to-model-to-display path before editing.
Then make the smallest change in these files. Preserve our agreed APIs.
Do not add libraries, rewrite the app, or change unrelated files.
Checks: solve A then B, select A; empty selection; solve again.
Report changes, checks actually run, and any checks I must run manually.

If the assistant cannot see your repository, provide the relevant methods and exact error text. Do not expect it to know files you have not shared. Keep passwords, API keys, private team/student information, and unrelated files out of prompts.

2. Good tasks are small and checkable

Assign a task with one observable outcome, relevant context, edit boundaries, and checks. These are examples; use the one your project needs.

Task to give an agentProof you supply or check
“Our game can collect a key. Implement opening one gate only when the player has the key. Put the rule in the model; change only these agreed files.”No key: gate stays shut. Key: gate opens. Repeat: no duplicate reward/effect.
“Explain and help add input validation to our existing linear solver. Preserve the calculation class and handle empty/nonnumeric entries.”Known answer works; invalid input gives feedback; next valid input replaces the error.
“Wire our simulation’s Step control to one model update using the selected parameter. Explain where state belongs.”A predictable initial state gives the expected next state; repeat and reset work.
“Our task objects already have completion state. Connect the selected-task button to that method and refresh the displayed list.”Only the selected task changes; no selection is safe; clicking again stays consistent.
“Review this visualization filter. Find why details still show an item after it is filtered out. Suggest the smallest fix.”Filter to zero/one/many matches; stale selection is cleared or updated correctly.

Task template: goal → current behavior → relevant files → allowed change → expected checks → explanation of the result.

3. Good practice and bad practice

AvoidDo this instead
“Build our whole game/app.”Ask for one feature with a concrete completion check; integrate it before expanding.
Paste a large answer over working code.Save a working commit, use a branch, and inspect each changed file.
“It crashes. Fix it.”Give reproduction steps, exact error/stack trace, expected result, actual result, and relevant code.
Accept new frameworks, patterns, or a giant class without question.Keep the existing stack; ask which object owns the rule and why the change is needed.
Trust a generated answer or test because AI says it is correct.Compute expected values yourself; run the app and compare. Treat unrun checks as unverified.
Repeatedly ask for another patch without understanding the failure.Reproduce the bug, form a hypothesis, test one change, and recheck the original behavior.
Let multiple teammates/agents change the same files independently.Agree on file ownership and method contracts; merge and test one PR at a time.
Merge code no teammate can explain or omit its source.Review the diff, explain the event/model/display path, and update citations and the AI Learning Log.

Skill A: Feature Coach — learn and implement a small feature

Download SKILL.md

---
name: feature-coach
description: Help students learn and implement a small JavaFX feature when they need an unfamiliar technique.
---

# Feature Coach

Use when: we need a feature or technique we do not yet understand.
1. Read the named code and restate current and desired behavior.
2. Identify the model object that should own the state/rule.
3. Explain the unfamiliar technique briefly; identify assumptions.
4. Suggest the smallest input-to-model-to-display increment.
5. Stay within the task's files, agreed APIs, and Java 21/JavaFX stack.
6. Implement that increment; do not add unrelated features or libraries.
7. Explain the diff and give normal, edge, and repeat checks.
8. Report checks actually run separately from manual checks still needed.
Done when: we can explain the change and verify the stated behavior.
Skill B: Bug Investigator — diagnose before patching

Download SKILL.md

---
name: bug-investigator
description: Diagnose and fix a reproducible JavaFX bug using expected and actual behavior.
---

# Bug Investigator

Use when: a reproducible feature fails.
1. Record steps, exact error, expected result, and actual result.
2. Trace the event, model state, and display; locate the first mismatch.
3. State one likely cause and a check that could disprove it.
4. Make the smallest justified fix in the agreed files.
5. Rerun the failing case and a previously working case.
6. Explain cause, fix, evidence, and remaining uncertainty.
Do not rewrite the app, hide exceptions, or remove checks to claim success.
Skill C: Behavior Checker — verify against expectations

Download SKILL.md

---
name: behavior-checker
description: Verify a completed feature with independent normal, edge, and repeated-use expectations.
---

# Behavior Checker

Use when: a feature is ready for verification.
1. Restate the written behavior, without assuming the code is correct.
2. Propose normal, edge, and repeated-use cases with concrete inputs.
3. Ask us to confirm expected results independently of generated code.
4. Check the two connected actions together, including state after reuse.
5. Use existing tests when useful; list manual GUI actions explicitly.
6. Record expected versus actual and fixes/retests.
Do not weaken expected behavior to match a failing implementation.
Do not claim GUI checks passed if you did not perform them.
Skill D: Team Reviewer — inspect a small change before merging

Download SKILL.md

---
name: team-reviewer
description: Review a scoped team change before a human merges its pull request.
---

# Team Reviewer

Use when: a teammate opens a feature PR.
1. Read the task and diff; check scope and agreed method contracts.
2. Check state ownership, duplicated rules, and unnecessary coupling.
3. Look for stale UI state, invalid input, and repeat/reset problems.
4. Confirm no unrelated files, credentials, or generated build output appear.
5. List concrete issues and checks; avoid broad style rewrites.
6. Let the human teammate review/merge; then test the combined main.
Done when: the reviewer understands the change and integration checks pass.

Make skills specific: name your real files, model objects, method contracts, and expected behavior in the task that follows the card. “Be a Java expert” alone gives the agent no useful boundaries or evidence standard.

Practical experiment: let AI coach your Git workflow

Work in pairs at your pod: one student operates, one reviews. Keep GitHub Desktop open on the same repository. Start with inspection; you do not need a conflict to complete the exercise. Do not deliberately break main.

Download team-git-check/SKILL.md. Install it in your tool’s skills folder as described above, or attach it to the chat. In Codex invoke $team-git-check; in Claude Code use /team-git-check; in Copilot ask it to follow the attached skill.

Task 1: repository health check — paste this first
Use team-git-check for this existing project. Inspect only; do not edit,
commit, switch branches, fetch, pull, push, or merge yet.
Report the repository root, current branch, modified/untracked files,
remote and upstream branch, and any unfinished merge.
Explain whether ahead/behind information may be stale.
Tell me the next safe step and why. Do not assume my branch is main.
  1. Inspect together. Compare the report with GitHub Desktop. If files are changed, review and commit intentional work on its feature branch before switching. Do not discard work just to obtain a clean tree.
  2. Get updated main. Ask for the phase below. Confirm the working tree is clean; let the agent explain the exact action before you approve it or perform it in Desktop.
  3. Share a small change. Create a fresh feature branch in Desktop. Add one useful run instruction to the project README, review it, and commit it. Ask for the named-branch push phase.
  4. Review and merge. Open a PR; your partner reviews it on GitHub. If main advanced, use the integration phase below first. The human reviewer merges the PR, then everyone updates main and runs the app.
Task 2: pull / push / integration phases — send one at a time
PULL PHASE:
Help me update main. Inspect first, then explain the exact action and wait
for my confirmation. With a clean tree, verify the upstream, fetch, and use
a fast-forward-only pull. Stop if main has diverged. Report what changed.

PUSH PHASE (replace the branch name with the actual name):
Help push my committed feature branch [actual branch]. Inspect its diff,
commits and upstream first. Explain the destination and wait for confirmation.
Push only this feature branch; do not push main or merge the PR.

INTEGRATION PHASE:
Help update my existing feature branch from updated main before PR review.
Verify both branch names and a clean tree. Explain main INTO feature and
wait for confirmation. If conflicts arise, show both intents and propose a
resolution; do not choose a side blindly. Help us test before completing
and pushing the merge. Feature INTO main will use a human-reviewed PR.

If a conflict occurs: read both changes, identify the intended combined behavior, inspect the resolved diff, and rerun the affected feature. A conflict-free merge can still break behavior. If the agent cannot run Git or authenticate, ask it to coach the equivalent Desktop pull and integration steps.

Experiment complete: both partners can explain pull versus push and the merge direction; the reviewed change is on main; the app still runs. Keep a brief note of what the agent recommended and what you verified. Continue to your real feature next.

5. Required before merging AI-assisted work

  • We can explain the new behavior and each changed responsibility.
  • The diff stays within the task and fits the existing project.
  • We independently checked normal, edge, and repeated-use results.
  • A teammate reviewed the change; the integrated main still runs.
  • We recorded the tool, assistance, what we learned, and help citation.

Follow Help Citation and AI Learning Log Policy. Use the existing log template. At check-in, explain one suggestion you accepted, changed, or rejected and the evidence behind that decision. The goal is verified learning, not a count of prompts.
