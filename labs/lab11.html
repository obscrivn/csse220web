Part 2: Abstract Classes: Dungeon Arena

You are playing a working console game: your hero battles a Goblin, then a Skeleton, in the Dungeon Arena. Goblin and Skeleton repeat the same fields and methods. An abstract Enemy class is already started for you, finish it, refactor Goblin and Skeleton to use it, and add one enemy of your own.

Learning Goals

  • Recognize duplicated state and behavior across related classes.
  • Inherit shared fields and methods from a superclass using extends.
  • Initialize shared state with super(...).
  • Declare an abstract method and override it with @Override.
  • Add a small Scanner-based input feature.

Time Completion Estimates: Part 2 is designed to take about 40 minutes once your project is open and running.

Step 1. Finish Enemy; refactor Goblin and Skeleton Required

A. Declare the abstract method

Open Enemy.java. It already has the shared name/health fields, a constructor, and getName/getHealth/isAlive/takeDamage. It is missing one thing:

  1. Declare public abstract String attack(Player player); in Enemy, do not give it a body there.

B. Refactor Goblin and Skeleton

  1. Make Goblin and Skeleton directly extend Enemy.
  2. Give each a constructor that calls super(name, health) with its fixed name and starting health (Goblin: "Goblin", 20; Skeleton: "Skeleton", 25).
  3. Remove their repeated fields and the four shared methods, inherit them from Enemy instead.
  4. Keep each class's own attack(Player player) method, but mark it @Override. This is how each enemy keeps its own damage amount and its own text.

Check: run MainApp and RunAllTests. The game plays the same way and all tests pass.

Keep these design rules
  • Store instance fields only in Enemy and keep them private.
  • Use Enemy's getters when subclass behavior needs that data.
  • Keep the existing public method signatures.
  • Constructors are not inherited, each subclass must declare its own and call super(...).
Step 2. Add a new enemy Required

Pick one: Dragon, Zombie, or Ice Golem (or propose your own).

  1. Create a new class that extends Enemy with its own name, starting health, and a fixed damage amount.
  2. Override attack(Player player) with its own text, using @Override.
  3. In MainApp, write a new battle method for it, following the same pattern as fightGoblin and fightSkeleton (for example, fightDragon(Player player, Dragon dragon, Scanner scanner)).
  4. Call your new method from main so the hero fights your enemy too.

Check: run MainApp. Your new enemy battle plays out the same way the Goblin and Skeleton battles do.

Why this matters

Classes with similar internals can share state and implementation through an abstract superclass. The superclass keeps the common work (the fields, the constructor, and methods like getHealth() and takeDamage()) in one place, and declares an abstract method for the one behavior every subclass must provide its own way. That is why adding a new enemy only meant writing one new class and one new method, instead of retyping the same fields and methods a third time.
