Lab 15: Drone Arena

Your goal: steer the drone with arrow keys and collect a blue energy orb.

Download DroneArena starter · Verification sheet

The completed Lab 13 behavior is provided. You will complete only three TODOs in ArrowApp.java. Keep SceneToken and its movement helpers unchanged.

How to follow this lab: complete Setup, then Steps 1–3 in order. Find the exact TODO shown, make the lettered edits, and run each checkpoint before continuing. Close the app before rerunning javafx:run. Ask your group lead to verify each finished step.
SetupRun the supplied app — no edits
  1. Extract DroneArena.zip. In IntelliJ, Open the DroneArena folder containing pom.xml.
  2. Use JDK 21 and Bundled Maven; set Maven Runner JRE to Project JDK. Reload Maven.
  3. In the Maven tool window, Execute Maven Goal: javafx:run.

You should now see… the drone and background. Start flies right and stops at the wall; Rotate turns it; Reset stops and restores it. Click the arena and press Right: it already works. No orb is visible yet.

Two controls: arrow keys move 10 pixels per key press; Start runs the existing animation. Holding a key uses your computer’s key repeat. Do not add another Timeline.

Step 1Move in all four directions

File: src/main/java/demo/ArrowApp.java

New idea: setOnKeyPressed runs a handler when a key is pressed. event.getCode() tells you which key. The supplied Right branch is your model.

1a. Read the working Right branch

if (code == KeyCode.RIGHT) {
    token.moveBy(10, 0, canvas.getWidth(), canvas.getHeight());

The first two arguments are horizontal and vertical changes. Right is (10, 0). Screen y increases downward.

1b. Add Left immediately after Right

At TODO 1, add this else if before the existing collision/consume block:

else if (code == KeyCode.LEFT) {
    token.moveBy(-10, 0, canvas.getWidth(), canvas.getHeight());
}

You should now see… Right and Left move the drone in opposite directions. Up and Down still do nothing at this point.

Optional OOP discussion — after your code works

The canvas receives the key event; SceneToken changes the drone’s position through moveBy. Receiving an event and changing state are separate jobs. This helper already pushes movement intelligence down to the object that owns the position. In a future design, a Drone class could own position and movement rules; the event handler would tell that drone to move.

Think: If the drone later needs a speed limit, should every key handler enforce it, or should the object owning movement enforce it?

Discussion only; no additional code or graded checkpoint.

Optional OOP discussion — after your code works

The drone and orb are separate scene objects with their own identity and state. The drone moves and rotates; the orb has a location and a collected/available state. The current orb is simply a Circle. Later, separate Drone and EnergyCrystal classes could keep each object’s related state and behavior together, giving each one a clear responsibility and high cohesion.

Think: Would a change to the orb’s reward value belong with the drone’s rotation code? Why?

Discussion only; no additional code or graded checkpoint.

Step 3Collect the orb on contact

File: src/main/java/demo/ArrowApp.java
Method/location: checkCollision(SceneToken token, Label status) → near the bottom of ArrowApp.java
Find this exact comment: TODO 3: Collect a visible overlapping orb and show a result.

New idea: bounds are a rectangle around a node. intersects reports whether two rectangles overlap. Both objects share canvas, so their parent-coordinate bounds can be compared.

3a. Check overlap inside checkCollision

boolean touching = token.getView().getBoundsInParent()
        .intersects(crystal.getBoundsInParent());

3b. Collect only a visible orb

Below that calculation, use this condition:

if (crystal.isVisible() && touching) {
    // Hide the orb.
    // Stop flight.
    // Show the collection message.
}

The visibility check matters: a hidden node still has bounds. It should be collected only once until Reset.

3c. Fill in the three actions

  1. Hide the orb with crystal.setVisible(false);.
  2. Stop the existing Timeline with its stop() method.
  3. Use status.setText(...) to display Energy collected! Reset to play again.

No new callers needed: collision checks already run after key movement, each animation tick, and rotation. Reset already restores the orb and drone. Stopping flight keeps an arrival-at-wall message from replacing the collection message.

You should now see… when you steer into the orb, it disappears and the collection message appears.

3d. Test the full interaction

  1. Reset. Press Start without steering: the drone should reach and collect the orb.
  2. Reset again: both objects should return.
  3. Click Start repeatedly before collection: flight should not speed up.

You should now see… collection works with both keyboard movement and animation, Reset restores the orb, and repeated Start clicks do not accelerate movement.

Checkpoint 3: ask your group lead to verify collection and Reset.

Why might contact count before the pictures visibly touch?

This is bounding-box overlap, not pixel-perfect collision. Transparent image corners can count as contact.

Optional OOP discussion — after your code works

Collection requires collaboration: drone position, orb availability, animation, and the status label all participate. The current small ArrowApp coordinates these objects in one method. A future GameController could coordinate collisions and scoring while Drone and EnergyCrystal manage their own state. That keeps either object from depending on unrelated controls and helps reduce coupling.

Think: Why would making EnergyCrystal directly change a status label and stop a Timeline create unnecessary dependencies?

Discussion only; no additional code or graded checkpoint.

From Demo to Game Architecture

Optional discussion: Drone could own position and movement; EnergyCrystal could own availability and reward; GameController could coordinate collection, score, and reset. How would you divide these responsibilities so each class has one clear job?

This is a possible future design. Keep today’s two-class application; no new classes, UML, written reflection, or submission are required for this discussion.

HelpIf something does not work
  • Keys do nothing: click the arena. Keep the supplied focus calls; do not create a second key handler.
  • Up moves down: use negative y for Up and positive y for Down.
  • No orb: use the supplied crystal field, set both coordinates, and add it to canvas.getChildren().
  • Orb follows the drone: remove it from the token Group; add it directly to canvas.
  • No collection: edit checkCollision, compare both bounds in parent coordinates, and check visibility.
  • Message gets replaced: stop flight when collecting.
