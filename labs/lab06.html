Lab Assignment 06: Refactoring as a Team

This lab is a short first refactoring exercise. Your goal is not to write a big new design from scratch. Your goal is to notice that the current structure is awkward, propose a small improvement, and preserve the program's behavior while changing the design.

Download starter project

Download the starter ZIP here: Lab06.zip

Open the project in IntelliJ and run GameApp.main(). You do not need any extra build setup for this lab.

👥 Pair Programming with CodeTogether

For this lab, you may work with your teammate using CodeTogether in IntelliJ.

Install CodeTogether

  1. In IntelliJ, open Settings → Plugins.
  2. Search for CodeTogether.
  3. Install the CodeTogether plugin.
  4. Restart IntelliJ if prompted.

Start a shared session

One teammate should:

  1. Open the Lab 06 project in IntelliJ.
  2. Open the CodeTogether tool window.
  3. Choose Host New Session.
  4. Copy the session link and send it to their teammate.

The other teammate can join using the shared link.

Both students should actively participate in the refactoring. Do not divide the lab into “you do one file, I do the other.” Work through the design decisions together.

Why this lab matters

Refactoring is about improving structure without changing the behavior the program is supposed to provide. A good refactoring makes the code easier to understand and easier to extend.

In this lab, the starter program already works, but it has a clear design problem: related item information is split across multiple structures, and one class is doing work that seems more natural for the item itself.

Run the starter program

Before editing anything, run GameApp and observe the output.

The program should:

  • add items to the treasure chest
  • remove an item
  • report how many items are stored
  • compute the total value
  • report whether an item is rare

Write down what the program does correctly before changing the design.

Inspect before you edit

Discuss these questions with your teammate before changing the code:

  • Which pieces of data always belong together?
  • Is there a noun in the scenario that is not currently represented as a class?
  • Does TreasureChest contain behavior that seems to belong to something else?
  • What structural change would remove the need to keep two collections synchronized?

The main idea is to identify one important design problem and fix it, not to rewrite the entire program.

Need a hint?

Look for places where item data is split across two lists. Ask yourself which data belongs together and which class should own the item-specific behavior.

Refactor together

Once your team agrees on one small structural improvement, refactor the code together. Keep the behavior the same while simplifying the design.

Focus on the most obvious design issue first. Your refactoring should be small and understandable.

  • Move related item data together.
  • Represent an item as an object instead of storing its parts separately.
  • Move item-specific behavior to the class that owns that information.
  • Update the chest to work with the refactored item representation.

Do not add large hierarchies, unnecessary abstractions, or extra requirements. This lab is meant to be a first, manageable refactoring activity.

Run and verify

After refactoring, run GameApp.main() again.

Your refactored version should still:

  • add items
  • remove items
  • count the number of items
  • calculate total value
  • determine whether an item is rare

If the output changes in a way that breaks the original behavior, you have likely changed too much or moved responsibilities incorrectly.

Generate UML from your final code

Use IntelliJ's UML/Class Diagram tool to generate a diagram from your completed Java code.

The key is that the UML should match what your team actually implemented, not what you intended to write.

Save or export the final diagram and include it in your submission.

Submit

Each team submits:

  1. The final UML diagram generated from the finished code
  2. A short reflection with approximately 3 questions:
  • What was the biggest design problem you identified in the starter code?
  • What did your team change, and why does that make the design easier to understand or extend?
  • How did you verify that the refactoring did not change the required program behavior?

Keep the reflection brief. This is a small design discussion, not a long essay.
