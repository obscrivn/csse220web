Skill 08: Debug, Test, and Improve AI-Assisted Java Code

Read the error, reproduce the bug, find the cause with evidence, and review every change before you commit it, whether you wrote it or an AI did.

  • CategoryDebugging and software design
  • DifficultyBeginner (for everyone)
  • ConceptsCompile vs. runtime vs. logic errors, stack traces, println, IntelliJ debugger, test cases, diffs
  • PrerequisitesNone. Use it any time.
  • EffortAbout 1 hour, then keep using it

1 Mission

Every feature in this hub will break at least once while you build it. AI assistants make this more important, not less: they produce code that looks right, compiles, and still does the wrong thing. The skill that separates a working team from a stuck one is debugging with evidence instead of guessing or asking for "another fix".

Your mission: learn to classify an error, read Java's messages, reproduce and diagnose a real bug planted in Drone Arena code, and review AI-written changes before they reach main.

2 What you already know

  • Homework tests: a failing test tells you expected vs. actual.
  • Lab 13 and Lab 15 "If something does not work" sections: each one maps a symptom to a cause. That is debugging.
  • Milestone 2 checks: the input/action | expected | actual | fix/retest table.
  • Errors & Exceptions (Week 8): what an exception is and how try / catch works.

3 Learn the concept

Runtime exceptionWhile runningA stack trace in the Run window; the app may not open, or a feature stops workingFind the deepest Caused by: and the first line in your package

Reading a compiler error

These are real messages produced by small mistakes in the Lab 15 code:

Mistake: token.moveBy(-10, 0); (forgot the width and height) 
demo/ArrowApp.java:76: error: method moveBy in class SceneToken cannot be applied to given types;
                token.moveBy(-10, 0);
                     ^
  required: double,double,double,double
  found:    int,int
  reason: actual and formal argument lists differ in length

Read it as: file ArrowApp.java, line 76. moveBy needs four doubles, and you passed two values. Open SceneToken.moveBy and compare the parameter list.

Mistake: crystl.setVisible(false); (typo) 
demo/ArrowApp.java:108: error: cannot find symbol
            crystl.setVisible(false);
            ^
  symbol:   variable crystl
  location: class ArrowApp

"cannot find symbol" means Java does not know that name: a typo, a missing import, a variable used outside its scope, or a method that does not exist. AI tools sometimes invent methods. This message is how you catch them.

Fix the first compiler error, then recompile. One mistake can cause several follow-on errors that disappear on their own.

Reading a stack trace

Here is the real output when the drone image path is wrong. getResource("/drone.png") is missing the images folder. Some JavaFX-internal lines are removed.

Exception in Application start method
java.lang.reflect.InvocationTargetException
	at java.base/jdk.internal.reflect.DirectMethodHandleAccessor.invoke(...)
	...
Caused by: java.lang.RuntimeException: Exception in Application start method
	at javafx.graphics@21.0.8/com.sun.javafx.application.LauncherImpl.launchApplication1(LauncherImpl.java:893)
	...
Caused by: java.lang.NullPointerException: Cannot invoke "java.net.URL.toExternalForm()"
    because the return value of "java.lang.Class.getResource(String)" is null
	at demo.SceneToken.<init>(SceneToken.java:18)
	at demo.ArrowApp.start(ArrowApp.java:25)
	at javafx.graphics@21.0.8/com.sun.javafx.application.LauncherImpl.lambda$launchApplication1$9(...)
	...
Exception running application demo.ArrowApp
  1. Skip to the last Caused by:. The earlier ones are JavaFX wrapping the real problem.
  2. Read the message. getResource(...) returned null, which means the file was not found at that path.
  3. Find the first line in your package (demo.): SceneToken.java:18. <init> means "inside the constructor".
  4. The next line is the caller: ArrowApp.start, line 25, which is new SceneToken().
  5. Fix the cause, not the symptom: correct the path to /images/drone.png. Do not wrap the line in try / catch to hide it.
Two setup errors that are not bugs in your code
  • Error: JavaFX runtime components are missing, and are required to run this application: you started your app class (the one that extends Application) with the green Run arrow. Start the app with the Maven goal javafx:run, as in every JavaFX lab. The green arrow is fine for check classes with no JavaFX in them.
  • The image works on your laptop but not on a teammate's: check the file name's capitalization. Drone.png and drone.png can look the same on some computers and differ on others. Match the name exactly.

Finding a logic error: the debugging loop

  1. Reproduce: write the exact steps that make the bug happen every time.
  2. Predict: state what should happen at each step.
  3. Observe: collect evidence about what actually happens, using print statements or the debugger.
  4. Hypothesize: "I think X happens because Y." Make one claim you can test.
  5. Change one thing, then rerun the reproduction steps.
  6. Retest everything nearby (normal, edge, repeat) so the fix did not break something else.

Two ways to observe

Print statements (always work)

System.out.println("checkCollision: visible="
        + crystal.isVisible() + " score=" + score.getScore());

Output appears in IntelliJ's Run window while javafx:run is running. Print the values your hypothesis is about. Remove the prints before you commit.

Breakpoints (IntelliJ debugger)

  • Click the gutter next to a line number to set a red breakpoint.
  • Click the green arrow next to main in a check class (such as ScoreKeeperCheck from Skill 04) and choose Debug. Execution pauses at the breakpoint, and the Variables panel shows every field and local.
  • Step Over (F8) runs one line; Step Into (F7) enters a method call; Resume continues.
  • javafx:run starts your app in a separate process, so breakpoints in GUI code usually do not stop there. Debug your model classes through a check class, and use prints for GUI handlers.

Inspecting AI-generated code

Before accepting any suggestion, ask:

  • Does it use my class, field, and method names, or did it invent some? (Look for "cannot find symbol".)
  • Does it add a second Timeline, a new library, a new framework, or a giant new class?
  • Which object now owns the state? Does that match our design?
  • Are there empty catch blocks, magic numbers, or copied code?
  • Does it handle the edge cases I listed, such as empty input, the last level, or a reset?
  • Can I explain every line to a teammate?

Not a game? The same skills apply
  • Solvers: logic errors hide in formulas. A check with a hand-computed answer is your best evidence (see Skill 07).
  • Input apps: runtime exceptions such as NumberFormatException mean that validation is missing (see Skill 06).
  • Data apps: IndexOutOfBoundsException in a stack trace points to the exact list or array access.

5 Design before coding (and before debugging)

Good design makes bugs easier to find. Before you change code to fix a bug, answer:

  1. Where is the single place this state changes? If the score can change in three places, that is your first suspect.
  2. Who calls this method, and how often? In Lab 15, checkCollision runs on every tick, every arrow key, and every Rotate.
  3. What is the expected value at each step? Write it down before you print or debug, so the evidence has something to be compared with.
  4. Can I reproduce this in a test? If the bug is in a model class, a check that prints FAIL is the best bug report.

6 Guided practice: the bug hunt

A teammate added scoring to Drone Arena. It compiles and runs, but players report that one orb is worth way too many points. Here is their checkCollision. Do not fix it yet.

Buggy on purpose 
private void checkCollision(SceneToken token, Label status) {
    boolean touching = token.getView().getBoundsInParent()
            .intersects(crystal.getBoundsInParent());
    if (touching) {
        crystal.setVisible(false);
        score.addPoints(ORB_POINTS);       // ORB_POINTS is 10
        updateScoreLabel();
        status.setText("Energy collected!");
    }
}
  1. Reproduce. Write the steps: "Reset, press Start, do not steer, wait until the drone passes the orb." In our test run, the score reached 390 for a single orb.
  2. Predict. How many times should points be awarded? Which call sites run checkCollision? (Look at the Timeline callback, the key handler, and Rotate.)
  3. Observe. Add one print as the first line inside the if: 
    System.out.println("award! visible=" + crystal.isVisible());
    Run the reproduction steps. How many lines appear? What does visible say after the first one?
  4. Hypothesize. Finish this sentence with your evidence: "Points are awarded repeatedly because ___, even though the orb is hidden."
    Check your hypothesis

    A hidden node still has bounds, so intersects keeps returning true. The Timeline is still running (this version never calls flight.stop()), so every 20 ms tick while the drone overlaps the orb awards 10 more points. The missing piece is a guard condition.

  5. Change one thing. Add the guard that makes the award happen only once. Decide whether the flight should also stop, as it did in Lab 15.
  6. Retest with the three checks in section 7, then remove the print statement.

Practice 2: review an AI suggestion

A student asked an assistant "add scoring to my drone game" and received this. It compiles. Find at least four problems before reading the hints.

AI-generated suggestion 
// AI suggestion: "Here's how to add scoring!"
Timeline scoreTimer = new Timeline(new KeyFrame(Duration.millis(20), e -> {
    try {
        if (token.getView().getBoundsInParent()
                .intersects(crystal.getBoundsInParent())) {
            score = score + 10;
            new Label("Score: " + score);
        }
    } catch (Exception ex) { }
}));
scoreTimer.setCycleCount(Timeline.INDEFINITE);
scoreTimer.play();
Hints: problems to look for
  • A second Timeline. It runs even before Start, and it is not stopped by Reset.
  • No guard, so the same duplicate scoring as above.
  • new Label(...) creates a label that is never added to the scene, so nothing on screen changes.
  • An empty catch silently hides any exception.
  • The score is a bare int changed inside a timer, not a model with rules (Skill 04).

Practice 3: review before you commit

  1. In GitHub Desktop → Changes, click each changed file and read the green and red lines of the diff.
  2. Uncheck files you did not mean to change, such as IDE settings or build output.
  3. Remove debugging prints and commented-out experiments.
  4. Make sure there are no new dependencies in pom.xml that the team did not agree on.
  5. Run the app and your tests after the final edit, not before it.
  6. Write a commit message that says what changed and why. Then push and open a pull request for review, as in the GitHub Desktop walkthrough.

7 Test your skill

Apply these to your bug-hunt fix:

  • NormalReset, then Start: the score becomes exactly 10 when the orb is collected. Collect it by steering instead: also exactly 10.
  • EdgeAfter collecting, press arrows, Rotate, and steer back over the orb's old position: the score stays at 10, and no stray prints are left in the Run window.
  • Repeat / resetCollect → Reset → collect, three times: the score behaves as your team designed, every time. Write the result in your checks table: input/action | expected | actual | fix/retest.

8 Extend the skill

Challenge: turn a bug into a regression test

Next time you find a bug in a model class, add a line to its check class that prints FAIL because of the bug, before you fix it. Fix the code, watch it change to PASS, and keep the check. If anyone (or any AI) reintroduces the bug later, rerunning the check catches it. Try it now: add a check showing that ScoreKeeper.addPoints(-5) must not lower the score, make it fail, then make it pass.

9 Ask your AI Coach

For debugging, ask the AI to coach you toward the cause instead of handing you a patch.

I am a CSSE220 student working on a Java 21 / JavaFX 21 project. I want to LEARN to debug this problem myself. Please act as a debugging coach.

What I expected: [expected behavior]
What actually happens: [actual behavior]
Steps to reproduce: [exact steps, every time]
Error message or stack trace (if any): [paste the full text]
Relevant code: [paste only the methods involved, with real class names]
What I already tried: [your attempts and what happened]

Please:
1. First tell me what kind of error this is (compile, runtime, or logic) and how you can tell.
2. If there is a stack trace, show me how to find the line in MY code that matters. Let me find it first.
3. Ask me questions that help me form a hypothesis. Do not give me the fix immediately.
4. Suggest one print statement or breakpoint that would test my hypothesis, and wait for my results.
5. After I propose a fix, ask me how I will retest normal, edge, and repeat/reset behavior.
6. If my code came from an AI, help me review it for invented methods, duplicated timers, empty catch blocks, and state in the wrong class.
Do not rewrite my whole project.
Using a coding agent to investigate?
  1. Context: the repository root, the exact reproduction steps, and the full error text.
  2. Narrow task: "Investigate only. Do not edit files. Explain the most likely cause and point to file:line evidence."
  3. Plan first: ask for the smallest fix and which tests would prove it, before any edit.
  4. Review the diff: a one-line bug usually has a small fix. Be suspicious of large rewrites.
  5. Run your reproduction steps and the three checks, then commit with a message describing the bug, and log the help.

10 Skill Unlocked

  1. Classify an error as compile, runtime, or logic, and read a compiler message or stack trace down to the line in your own code.
  2. Demonstrate the debugging loop on a real bug: reproduction steps, evidence, hypothesis, one change, retest.
  3. Review an AI-generated change and name specific problems before you accept, edit, or reject it.
