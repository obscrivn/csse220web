Share Your Branch and Get Team Updates

A GitHub Desktop checklist for teams already working on branches.

To get teammates’ work into your unfinished branch: save your work → update local main → merge main into your branch. Follow A, B, then C.

To put your finished work into main: follow A–C first, then open a reviewed pull request in D. After it is merged, everyone follows B.

Example: your branch is sam-score. Replace that name below with your actual branch name.

A. SaveB. Get mainC. Update my branchD. Share my workE. Next taskIf stuck

Use GitHub Desktop for Git steps, IntelliJ to edit/run, and the GitHub website to review/merge a pull request. Keep using the same project folder. Do not clone again or copy files between branches.

A. Save your branch work first

  1. IntelliJ: choose File → Save All.
  2. Desktop: check Current Repository and Current Branch. The branch should be your own, such as sam-score.
  3. Open Changes. Review your files, select the intended changes, enter a short Summary, and click Commit to sam-score. If there are no local changes, skip this commit.
  4. Click Publish branch if this branch has never been uploaded; otherwise click Push origin when offered. Wait for completion.

Ready: Changes says No local changes, and your commits are uploaded to your branch. Commit saves on your computer; push uploads to GitHub. Neither adds your work to main.

If your edits are on main or an unexpected branch, stop and ask for help before switching. Do not discard edits.

B. Get teammates’ merged work onto your local main

Before you start: your teammate’s PR must say Merged on GitHub. Work still only on their feature branch is not in main yet.

  1. Desktop: click Current Branch, then select main.
  2. Check the top: Current Branch = main.
  3. Click Fetch origin and wait.
  4. If Pull origin appears, click it and wait. If no incoming updates are offered, your local main is current.
  5. IntelliJ: check for your teammate’s change and run the app using clean javafx:run.

Result: your local main now contains the team’s merged changes. Your own branch has not received them yet. Continue to C if your task is unfinished.

Fetch checks/downloads remote history. Pull updates the branch currently selected. Clicking Pull while on sam-score does not automatically bring main into it. No new commit is needed just to save pulled commits.

C. Bring updated main INTO your unfinished branch

Do B first. Local main must be up to date, and Changes must show no local changes.

  1. Desktop: click Current Branch → sam-score.
  2. Check the top: Current Branch = sam-score. This is the branch receiving the changes.
  3. Open Current Branch again. At the bottom, click Choose a branch to merge into sam-score.
  4. Select main. Check the button says Merge main into sam-score, then click it. If the branch is already up to date, skip the merge.
  5. If a conflict appears, stop and use the help below with your teammate. Otherwise let the merge finish.
  6. IntelliJ: check that your work and your teammate’s work are both present. Run the app and test both features together.
  7. If you fixed code, save and commit those fixes on sam-score. Click Push origin to upload the merge and any fixes. A completed ordinary merge is already recorded by Git.

Direction: main → sam-score. You are adding team updates to your branch. Your work still reaches main through the PR in D.

D. Put your finished branch INTO main

  1. Stay on sam-score. Confirm your changes are committed, pushed, and tested with the latest main from C.
  2. Desktop: click Preview Pull Request → Create Pull Request (or Create Pull Request if shown). This opens the GitHub website.
  3. GitHub website: check base: main and compare: sam-score. The base receives your work.
  4. Write what changed and how you tested it. Click Create pull request. If a PR already exists for your branch, open it; new pushed commits update it automatically.
  5. Ask a teammate to review Files changed and test the feature. Make requested fixes on the same branch, then commit/push them.
  6. When reviewed and ready, the designated reviewer clicks Merge pull request → Confirm merge on GitHub. Wait until it says Merged.
  7. Everyone, including you: follow B to pull the new main. Teammates with unfinished branches then follow C.

Result: sam-score → main through the reviewed PR. Publishing/pushing a branch or merely opening a PR is not a completed merge.

One PR at a time: after the first is merged, the next author repeats B and C, tests, and then asks for their PR to be merged. If main changes during review, refresh your branch with B/C and test again.

E. Start the next task from updated main

  1. After your PR is merged, follow B and stay on main.
  2. In Desktop choose Current Branch → New Branch. Give the new task a clear name and create it from updated main.
  3. Check the new branch name before editing in IntelliJ.

Use a fresh branch for a new task. Keep an unfinished branch only when continuing its current task.

If something looks wrong

  • Switching asks what to do with local changes: cancel the switch and return to A. Save/commit intentional work before trying again.
  • Teammate’s update is missing: check their PR says Merged, then B updates main and C updates your branch. Check IntelliJ and Desktop use the same folder.
  • Merge conflict: pause. With the author of the other change, inspect the conflicting file in IntelliJ. Decide the combined behavior and keep the needed parts of both changes. If unsure, ask the instructor before completing the merge. Follow Desktop’s conflict-resolution prompts only after reviewing the resolved file; test before pushing.
  • Git merges without a conflict, but the app breaks: integration still needs testing. Fix it on the feature branch before merging its PR.
  • No merge button, blocked pull, or unexpected history: ask for help. Do not discard files, force-push, or delete the repository to get past the problem.
