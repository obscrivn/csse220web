Milestone 1: one team repository, one local copy per student

Order: setup lead downloads → runs starter → initializes local Git → publishes to GitHub → invites team. Other students accept → clone → open → run. Then everyone branches → edits a different file → commits → pushes → requests review → merges → pulls main.

Teammates: wait for the setup lead. Only the lead performs Steps 2–3. Everyone else waits until the lead publishes the starter and invites them. While waiting, you may prepare your GitHub account, install the tools, and create the local folder below. Do not create a repository, download another starter, or start cloning in GitHub Desktop. Begin Step 4 only after receiving and accepting the invitation.

If the instructor already supplied a team repository, use that repository and skip creation. If your team already has code or commits, ask the instructor how to bring the starter into that repository before copying files. Do not create a competing repository.

1. Everyone: prepare

  1. Have a GitHub account, GitHub Desktop, IntelliJ IDEA, and JDK 21 ready.
  2. If you are the setup lead, sign in to GitHub Desktop with your own account and check its Git name and email settings. Other teammates wait until Step 4 to begin the GitHub Desktop repository steps.
  3. Choose one setup lead. Agree on a team repository name and who owns it; the setup lead will share its URL after publishing. Use the instructor's visibility requirement; if none is given, keep the repository private and invite the instructor if access is needed.

Create a local course folder (everyone)

Use File Explorer on Windows or Finder on macOS to create a folder named CSSE220FinalProject directly inside your user/home folder. Examples (replace YourName with your computer username):

  • Windows: C:\Users\YourName\CSSE220FinalProject
  • macOS: /Users/YourName/CSSE220FinalProject (Finder → Go → Home, then File → New Folder)

Keep the repository outside OneDrive and other cloud-sync folders. On Windows, Desktop and Documents may be redirected into OneDrive even when they look local. In File Explorer, click the address bar and check the full path; if it contains OneDrive, choose a different location. On macOS, avoid iCloud Drive and any synced Desktop/Documents folders. Also avoid Dropbox and Google Drive folders. Cloud sync can interfere with Git's frequent file updates. Use GitHub Desktop to share project changes.

The setup lead puts the extracted starter here. Other teammates choose a new folder here as the clone destination after accepting their invitations. Do not put one Git repository inside another.

2. Setup lead only: download and run first

  1. Download Milestone1Starter.zip, then unzip/extract it before opening it. On Windows, right-click the ZIP → Extract All; on macOS, double-click the ZIP. Do not open the project from inside the ZIP preview.
  2. Move the extracted Milestone1Starter folder into the local CSSE220FinalProject folder described above, outside any existing Git repository. Check the full path: it must not contain OneDrive. Do not work inside the ZIP or a temporary preview.
  3. Open the folder containing pom.xml in IntelliJ with File → Open. Let Maven load, select JDK 21, and open View → Tool Windows → Maven. In that tool window choose Execute Maven Goal, enter clean javafx:run, and run it. If the Maven project is missing, use Add Maven Projects and select pom.xml. Set both the project SDK and Maven runner JRE to JDK 21. IntelliJ bundles Maven.
  4. Check that the window opens and its button changes the message. Close the app.

Checkpoint: the unchanged starter runs before anyone initializes Git or changes the Java code.

Check the folder before initializing Git

Use one parent folder name throughout this guide: CSSE220FinalProject. Create it directly inside your user/home folder, outside OneDrive or other cloud-sync folders. After unzipping, arrange the starter like this:


CSSE220FinalProject/          ← local parent folder; not a Git repository

└── Milestone1Starter/        ← select this project folder in Desktop and IntelliJ

    ├── pom.xml

    ├── README.md

    ├── .gitignore

    └── src/

Check in File Explorer/Finder: open Milestone1Starter. You should immediately see pom.xml and src/. If you see only another folder named Milestone1Starter, open that inner folder to find the actual project. You may move the actual project folder into CSSE220FinalProject before initializing Git, provided the destination does not already contain another project; do not overwrite or combine folders.

Two dialogs use different folder selections:

  • Add Local Repository → Choose: select CSSE220FinalProject/Milestone1Starter, the folder containing pom.xml.
  • Create Repository (if prompted) → Name: Milestone1Starter.
  • Create Repository (if prompted) → Local path: select only the parent CSSE220FinalProject folder. Desktop combines Local path + Name to form the repository path.

Before clicking Create Repository: the resulting path should end in CSSE220FinalProject/Milestone1Starter, with the project name appearing once. If it ends in Milestone1Starter/Milestone1Starter, change Local path to the parent folder. Keep the supplied README and .gitignore and do not select replacement templates.

After creating it: use GitHub Desktop → Repository → Show in Finder / Show in Explorer. The folder that opens must directly contain pom.xml and src/. If it opens an empty folder or a folder containing only another project folder, stop before committing or publishing and ask the instructor to check the path. Do not delete .git or move files around to repair an initialized repository yourself.

3. Setup lead only: initialize this folder, then publish

  1. In GitHub Desktop, choose File → Add Local Repository → Choose (Windows may use lower-case wording). Select the extracted Milestone1Starter folder that directly contains pom.xml, README.md, .gitignore, and src/. For example: C:\Users\YourName\CSSE220FinalProject\Milestone1Starter or /Users/YourName/CSSE220FinalProject/Milestone1Starter. Select this same folder in IntelliJ. Do not select the ZIP, the parent CSSE220FinalProject folder, or src/. If extraction produced an extra outer folder, open it and select the inner folder containing pom.xml.
  2. Because a ZIP is not a Git repository, Desktop should offer to create a repository here. Use that option. Confirm the resulting repository path is the existing starter folder, not a new folder inside it. If the dialog asks for Name and Local path, use Milestone1Starter as Name and its parent folder as Local path; inspect the resulting path before continuing.
  3. Keep the supplied README and .gitignore; do not replace them with generated templates. Create the repository. This initializes local Git, equivalent to git init; it has not uploaded anything.
  4. Confirm Current Branch is main. If it has another name, use Branch → Rename to change it to main before publishing or inviting anyone.
  5. Inspect History and Changes. Repository creation may already have made the initial commit. Confirm pom.xml, README, .gitignore, and src/main/java/finalproject/StarterApp.java are included in history. If needed, select these files and commit with message Add JavaFX starter on main.
  6. Build output must not be committed: no target/, .class, .jar, .idea/, or .DS_Store files should be selected. The supplied .gitignore also excludes IntelliJ *.iml files, other IDE settings, logs, and editor backup files. Keep .gitignore itself tracked. Java source, pom.xml, Markdown, and app resources such as FXML, CSS, images, and JSON should remain trackable.
  7. Click Publish repository. Choose the agreed team repository name and visibility, then publish. Do not separately create an empty repository on GitHub first for this workflow.
  8. Use Repository → View on GitHub. Verify the main branch contains pom.xml and src/ at its root, rather than inside another Milestone1Starter/ folder.
  9. On GitHub open repository Settings → Collaborators (or Collaborators and teams), add each teammate by username, and send the repository URL to your team. Each teammate must accept the invitation.

Checkpoint: everyone can open the same repository URL and see the starter files. The setup lead keeps using this local folder; the lead does not need to clone it again. This initial baseline commit is the one setup exception to doing work on feature branches.

4. Other teammates: clone, then open the cloned code

  1. Wait until the setup lead finishes Steps 2–3 and sends your invitation and the team repository URL. Accept the invitation on GitHub in your web browser while signed in to your own account. Confirm you can see the starter files in the repository before continuing.
  2. Now open GitHub Desktop and sign in with that same account. Check your Git name/email in Desktop settings. Choose File → Clone repository → URL and paste the team's URL.
  3. Under Local path, choose a new repository folder inside your local CSSE220FinalProject folder, outside any existing Git repository. For example: C:\Users\YourName\CSSE220FinalProject\TeamProject on Windows or /Users/YourName/CSSE220FinalProject/TeamProject on macOS. Check that the full path does not contain OneDrive and is not inside another cloud-synced folder. Do not clone into an extracted starter folder. Click Clone.
  4. Confirm Current Repository is your team's repository and Current Branch is main.
  5. Use Repository → Show in Finder / Show in Explorer to identify the clone's actual location.
  6. In IntelliJ choose File → Open and select that cloned folder containing pom.xml. Let Maven load and select JDK 21.
  7. Run Maven goal clean javafx:run and check the same window/button behavior. Close the app.

Checkpoint: every student runs their own clone. Do not download another ZIP, copy a teammate's .git folder, fork the repository, or make a second team repository.

5. Everyone: agree on different files, then branch

Where to work: create and switch branches, commit, push, fetch, and pull in GitHub Desktop. Edit Java and documentation in IntelliJ. Review and merge pull requests on the GitHub website.

For this first practice, use documentation files so the single Java class does not become a collision point. These files are not supplied in the ZIP; create them during the exercise.

StudentExample branchOnly file this student creates/edits
Alexalex-project-ideadocs/idea.md
Samsam-designdocs/design.md
Jojo-team-plandocs/team-plan.md

Adapt names to your team. For larger teams use another unique file, such as docs/testing-plan.md. The shared folder name docs/ is fine; each student must own a different file. Assign one owner for shared files such as StarterApp.java, pom.xml, and README during this exercise.

  1. Save files and check Desktop's Changes tab. Finish and commit any intended work on its existing branch before switching; if unexpected changes are present, stop and ask for help. Do not discard them.
  2. In GitHub Desktop, select Current Branch at the top of the window → main.
  3. Click Fetch origin, then Pull origin if it appears. Fetch checks for updates; pull downloads them into your local branch. Fetch alone does not update your working files.
  4. Stay in GitHub Desktop. At the top of its window, click Current Branch → New Branch. Enter your branch name, choose main as the base, and click Create Branch. Create this branch in GitHub Desktop, not in IntelliJ or on the GitHub website.
  5. In GitHub Desktop, verify Current Branch shows your feature branch. Then return to IntelliJ to edit the files. IntelliJ uses the branch selected in Desktop because both apps are using the same local repository folder.

6. Everyone: edit, commit, and push your own branch

  1. In the repository folder open in IntelliJ, create docs/ if needed and your assigned Markdown file. Add a short contribution: idea/user/first interaction, class responsibilities, or team tasks. Save it.
  2. In GitHub Desktop verify both repository and branch. Inspect Changes: only your intended file should appear. Stop if you see generated files or files you did not mean to edit.
  3. Select your file, enter a message such as Add initial class responsibilities, and click Commit to [your branch].
  4. Click Publish branch the first time, or Push origin for later commits.
  5. View the branch on GitHub and check that your file and commit appear there.

A commit saves locally; push uploads commits. Neither action merges your work into main.

7. Everyone: open a pull request

  1. In Desktop choose Create Pull Request, or Preview Pull Request then Create Pull Request if offered. On GitHub you can also use Pull requests → New pull request.
  2. Set base: main and compare: your branch in the shared team repository.
  3. Check Files changed. It should show your intended file, not another teammate's changes.
  4. Give the PR a short title and explain what you changed and how you checked it. Request a teammate's review. Each student opens their own PR using their own account.

8. Team: review and merge one PR at a time

  1. A different teammate opens the PR and reads Files changed. Check the content, the file ownership agreement, and any requested corrections. For Java changes, first commit any outstanding local work, click Fetch origin in Desktop, select the author’s branch under Current Branch, and run it in IntelliJ before approving. Return to your own branch afterward. For this documentation-only exercise, read the changed file on GitHub.
  2. If corrections are needed, the author edits on the same feature branch, commits, and pushes again. The existing PR updates automatically.
  3. When approved, the designated reviewer or setup lead uses Merge pull request on GitHub and confirms the merge. If the repository offers a different enabled merge method, use the instructor's chosen method. Wait for the PR to show Merged before handling the next PR.
  4. Recheck the next PR against the now-current main. For this practice, separate new documentation files should combine automatically. Different files reduce text conflicts but do not guarantee that Java features will work together.
  5. If GitHub reports a conflict, leave the PR open and ask the instructor for help. Do not overwrite one version, discard work, or force-push. If a repository rule requires the branch to be updated first, use the update procedure below.

9. Everyone: pull the combined result

  1. In Desktop confirm there are no uncommitted edits, then select Current Branch → main.
  2. Click Fetch origin, then Pull origin if offered.
  3. Open the project in IntelliJ. Verify all teammates' files are present and run clean javafx:run again.
  4. Record each student's PR URL and verify that all PRs show Merged. Create the next task branch from this updated main.

Switching branches: save your edits in IntelliJ, commit them on the correct branch in GitHub Desktop, then use GitHub Desktop → Current Branch → the desired branch. Desktop changes the files in the same local folder; IntelliJ should show those changes. You do not download or open a separate folder for each branch. If Desktop offers to carry uncommitted edits between branches and you are unsure where they belong, cancel and get help.

Continuing an existing feature branch after a teammate merges: pulling main does not update your other branches. With your edits committed, switch to main, fetch and pull; switch back to your feature branch; choose Current Branch → Choose a branch to merge into [your feature branch] → main → Merge main into [your feature branch]. If successful, run the app and push your branch. Stop for help if a conflict appears. New tasks should normally start on a fresh branch from updated main.

Quick recovery checks

  • Cannot clone/push: check the exact team URL, accepted invitation, signed-in account, and write access. Do not create a substitute repository.
  • Changes missing: save in IntelliJ; verify its open folder matches Desktop's repository folder and check Current Branch.
  • Branch missing on another computer: author must publish/push; others fetch. An unpublished branch exists only on its author's machine.
  • Hundreds of generated files: inspect .gitignore before committing. Ignoring a file does not untrack something already committed; ask for help if generated files are in history.
  • “JavaFX runtime components are missing”: use Maven clean javafx:run and check JDK 21.
  • Local changes prevent switching/pulling: keep them intact; ask for help choosing the correct branch. Never use force push or delete .git as a repair.

Vocabulary

Repository = files plus history. Clone = create a local working copy. Branch = a line of work. Commit = local snapshot. Push = upload commits. Pull request = proposal to review and merge. Merge = combine histories/changes. Fetch = check/download remote history without changing working files. Pull = bring remote changes into the current local branch.
