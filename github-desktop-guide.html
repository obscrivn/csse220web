Get your team started with GitHub

By the end of this guide, everyone on your team will have the JavaFX starter running and will have shared one small change with the team.

Choose one team lead for setup. The lead goes first. Everyone else waits for an invitation before cloning. You can install the tools and plan your project together while you wait.

Who are you?Where do you start?
Team leadDo Step 1, then Steps 2–3. Join everyone at Step 5. You do not need to clone.
Other teammateDo Step 1, wait for your invitation, then do Step 4. Join everyone at Step 5.

Use GitHub Desktop for branches, commits, push, and pull. Use IntelliJ to edit and run your code. The GitHub website is where you accept invitations and review and merge pull requests.

Already have a team repository or code you want to keep? Check with your instructor before creating another repository or copying files into it.

1. Everyone: choose a place for your project

Have your GitHub account, GitHub Desktop, IntelliJ, and JDK 21 ready. Each student uses their own GitHub account.

Create a folder named CSSE220FinalProject inside your user/home folder. Replace YourName below with your computer username:

  • Windows: C:\Users\YourName\CSSE220FinalProject. In File Explorer, go to your user folder and create the new folder there.
  • macOS: /Users/YourName/CSSE220FinalProject. In Finder, choose Go → Home, then File → New Folder.

Keep this folder outside OneDrive, iCloud Drive, Dropbox, and Google Drive. Desktop and Documents may sync automatically. On Windows, click File Explorer’s address bar to check the full path. If it includes OneDrive, choose a different location. GitHub will handle sharing your project files.

Your files will eventually look like this:


CSSE220FinalProject/       ← holds your project; leave this folder alone

└── Milestone1Starter/     ← your actual project folder

    ├── pom.xml

    ├── README.md

    ├── .gitignore

    └── src/

The starter becomes your project. Keep working in Milestone1Starter as your app grows. GitHub Desktop and IntelliJ should both use this folder. You do not need a second “real project” folder.

2. Team lead only: unzip and run the starter

Other teammates: wait for your invitation. Skip Steps 2–3.

  1. Download Milestone1Starter.zip.
  2. Unzip it. On Windows, right-click the ZIP and choose Extract All. On macOS, double-click it.
  3. Move the extracted Milestone1Starter folder into your local CSSE220FinalProject folder.
  4. Open Milestone1Starter in File Explorer/Finder. You should immediately see pom.xml and src/. If you see another Milestone1Starter folder instead, open that inner folder to find the actual project. Arrange it as shown above before creating the Git repository. Do not overwrite an existing project.
  5. In IntelliJ → File → Open, select the folder containing pom.xml. Do not create a new IntelliJ project.
  6. Let Maven load the project. Select JDK 21 for both the project SDK and Maven runner JRE.
  7. Open View → Tool Windows → Maven. Choose Execute Maven Goal, enter clean javafx:run, and run it. If the project is missing from Maven, use Add Maven Projects and select pom.xml.

You should see: a window titled “CSSE220 Team Starter.” Click its button. The message should change to “Your team has launched the shared starter.” Close the window before continuing.

IntelliJ includes Maven; you do not need to install it separately. Use the Maven goal above rather than the run arrow beside StarterApp.

3. Team lead only: put the starter on GitHub

Create the local repository

A repository is your project files plus their saved Git history. This first step creates that history on your computer; it does not upload anything yet.

  1. Sign in to GitHub Desktop with your own account. Check your Git name and email in Desktop’s settings.
  2. Choose File → New Repository. Fill in the dialog like this:
FieldWhat to enter
NameMilestone1Starter, exactly matching the extracted folder name
DescriptionOptional: a short description of your team’s project
Local PathYour parent folder, CSSE220FinalProject
Initialize this repository with a READMELeave unchecked; we supplied README.md
Git ignoreLeave None; we supplied .gitignore
LicenseLeave None for this exercise

Check before you click: Desktop combines Local Path + Name. The result must be the existing folder CSSE220FinalProject/Milestone1Starter containing pom.xml. If you see Milestone1Starter/Milestone1Starter, change Local Path to the parent folder.

  1. Click Create Repository.
  2. Choose Repository → Show in Finder / Show in Explorer. The folder that opens should directly contain pom.xml and src/. If it is empty or contains only another project folder, ask your instructor to check it before continuing.
  3. Check Current Branch at the top of Desktop. It should say main. If needed, use Branch → Rename to name it main.

The Git ignore dropdown says None because you are not adding a new template. Your supplied .gitignore still works. It keeps build output and computer settings out of the repository. Keep .gitignore itself with the project. Your file browser may hide this dotfile; that does not mean it is missing. You do not need to create another one.

Check your first commit

A commit saves a snapshot of your files in Git on your computer.

  1. In Desktop, click History on the left. Desktop may already have made an Initial commit.
  2. Click that commit. Check that it includes pom.xml, README.md, .gitignore, and src/main/java/finalproject/StarterApp.java.
  3. If those files are already in History and Changes is empty, your first commit is done. Go to “Upload and invite” below.
  4. If starter files are still listed under Changes, review them and select their checkboxes. Enter Add JavaFX starter in Summary (required) at the bottom left. Click Commit to main, then check History again.

You should see: the starter files in your commit. You should not see target/, .class, generated .jar files, or .idea/. If you do, ask for help before uploading. Java source, app resources, and your planning files should stay in the repository.

This first setup commit on main is the exception. After setup, everyone makes changes on feature branches.

Upload and invite

  1. Click Publish repository in Desktop. Enter your agreed team repository name and visibility, then confirm Publish Repository. If your instructor has not specified visibility, keep it private.
  2. Wait for the upload. If Push origin appears afterward, click it to send any remaining commits.
  3. Choose Repository → View on GitHub. On the main branch, check that pom.xml and src/ are visible immediately, rather than inside another folder.
  4. On GitHub, open Settings → Collaborators (or Collaborators and teams). Invite every teammate by username. Invite your instructor if they need access.
  5. Send your teammates the repository URL and tell them they can start Step 4.

You are ready when: the files are visible on GitHub and every teammate has an invitation. Keep using your existing local folder; you do not need to clone it again.

Remember: Publish repository is the first upload. Later, Push origin uploads new commits. A new feature branch uses Publish branch the first time you share it.

4. Other teammates: accept, clone, and run

Start only after the lead sends your invitation and the team URL. Do not download the starter ZIP or use New Repository.

  1. In your browser, sign in to your own GitHub account and accept the invitation. Open the team URL and check that you can see the files.
  2. Open GitHub Desktop and sign in with the same account. Check your Git name and email in its settings.
  3. Choose File → Clone repository → URL. Paste the URL your lead sent.
  4. Set Local path to the full destination, including the new project folder at the end:
  • Windows: C:\Users\YourName\CSSE220FinalProject\Milestone1Starter
  • macOS: /Users/YourName/CSSE220FinalProject/Milestone1Starter
  1. Read the complete path before clicking Clone. If Choose selected only CSSE220FinalProject, add Milestone1Starter at the end. If Desktop already added the project folder name, do not add it again. Let Desktop create this new folder; do not clone into an extracted starter or another Git repository.
  2. Click Clone and wait. If Desktop says the destination is not empty, choose a new, unused location or ask for help. Do not overwrite your files.
  3. Check Current Repository is the team repository and Current Branch is main.
  4. Choose Repository → Show in Finder / Show in Explorer. You should immediately see pom.xml, README.md, .gitignore, and src/.
  5. In IntelliJ → File → Open, select that same folder containing pom.xml. Let Maven load, select JDK 21, and run clean javafx:run as described in Step 2.

You should see: the same working starter window as your lead. Your clone is now your working project; use it for the rest of the milestone. The repository’s name on GitHub may differ from your local folder name. That is fine as long as everyone uses the same team URL.

5. Everyone: choose your file and create a branch

For this first practice, give each person a different file. You will create these files; they are not in the ZIP.

PersonExample branchFile they create
Alexalex-project-ideadocs/idea.md
Samsam-designdocs/design.md
Jojo-team-plandocs/team-plan.md

Use your own names. If you have more teammates, assign another file such as docs/testing-plan.md. Pick one owner for shared files like StarterApp.java and pom.xml so everyone is not editing them at once.

  1. In GitHub Desktop, check Changes. If you just finished setup, it should say No local changes. If you already have edits, save and commit them on their own branch before switching; use Step 6 below for the commit buttons. Ask for help if the edits are unexpected.
  2. Click Current Branch → main.
  3. Click Fetch origin, then Pull origin if it appears. If no incoming commits are offered, main is already current.
  4. Click Current Branch → New Branch. Enter your branch name, choose main as its base, and click Create Branch.
  5. Check the top of Desktop: it should now show your feature branch, such as sam-design.

Now return to IntelliJ to edit. You create and switch branches in GitHub Desktop. Both apps use the same project folder, so IntelliJ shows the branch you selected in Desktop.

6. Everyone: make a change, commit, and push

  1. In IntelliJ, create the docs folder in your project, then create your assigned file. Add a short contribution: your user and idea, planned class responsibilities, or the team’s next tasks.
  2. Choose File → Save All in IntelliJ.
  3. Open GitHub Desktop. Check the repository and your feature branch at the top.
  4. Click Changes on the left. Click each changed file and read what you changed. Select the checkboxes for the files you want in this commit.
  5. In Summary (required) at the bottom left, write a short message such as Add class responsibilities.
  6. Click Commit to [your branch]. Your change is now saved in local Git history.
  7. Click Publish branch for the first upload of this branch, or Push origin for later commits. Wait for it to finish.

You should see: your branch and its new file on GitHub. Commit saves locally; push uploads. Your change is still on your branch and has not joined main yet.

7. Ask a teammate to review your change

A pull request (PR) asks the team to review your branch before adding it to main. Each student opens their own PR.

  1. In Desktop, choose Create Pull Request, or Preview Pull Request → Create Pull Request if that is what your version shows. This opens GitHub in your browser.
  2. Check base: main and compare: your feature branch. This means “add my branch’s changes to main.”
  3. Open Files changed and check that it shows your intended file.
  4. Give the PR a short title. Say what you changed and how you checked it. Ask a teammate to review it.
  5. The reviewer reads the change. For this first documentation exercise, read the file on GitHub. For Java changes, save/commit any current work, fetch in Desktop, switch to the author’s branch, and run the app before approving.
  6. If the reviewer requests a correction, edit the file on the same feature branch, commit, and push again. The PR updates automatically.

You are ready to merge when: a teammate has reviewed your work and the change is ready to share.

8. Everyone: get the latest main

Use these steps after a PR is merged and before starting a new task. Keep using the same folder; you do not need to clone again.

  1. Save in IntelliJ: choose File → Save All.
  2. Keep your current work safe: open Desktop and check your feature branch. If files are listed under Changes, review and commit them using Step 6, then publish/push. If Changes says No local changes, skip the commit. If your edits are on main or an unexpected branch, ask for help before switching.
  3. Switch to main: in Desktop, click Current Branch → main. Check that the top now says main. The files in IntelliJ may change; your committed feature work is still saved on its branch.
  4. Check for updates: click Fetch origin and wait. Fetch checks GitHub; it does not update the files you are editing.
  5. Bring updates into your folder: if Pull origin appears, click it and wait. If no incoming commits are offered, you already have the latest main. You do not need to commit the downloaded changes.
  6. Check in IntelliJ: find your teammate’s merged changes and run clean javafx:run. If the changes are missing or the app fails, check with your teammate before adding more work.
  7. Choose your next step: for a new task, use Current Branch → New Branch in Desktop and start from this updated main. To continue an unfinished branch, follow Step 9C instead.

You should see: the team’s merged changes on your local main, and a working app. Choose your task’s feature branch before you start editing again.

9. Team: combine everyone’s work, one branch at a time

Suppose Alex and Sam edited different files. The team agrees to merge Alex’s work first. Follow this example, replacing the names with your own.

A. Agree, review, and merge the first PR

  1. Agree on the merge order. Everyone saves, commits, and pushes their feature-branch work. Pause edits to shared files while you combine changes.
  2. A teammate reviews Alex’s PR as described in Step 7.
  3. When it is ready, one designated reviewer/lead clicks Merge pull request on GitHub and confirms. Wait until the PR says Merged.

Alex’s work is now in the shared main on GitHub. Use a PR for this step; do not also merge Alex’s branch directly into main in Desktop.

B. Everyone: pull the updated main

Follow Step 8 on every computer, including Alex’s. Check that you can see Alex’s change and run the app.

If your own branch has been merged, start your next task on a new branch from updated main. Sam’s work has not been merged yet, so Sam continues below.

C. Next author: bring main into your unfinished branch

Sam needs Alex’s changes on sam-design before sharing the next change. Sam does these steps in GitHub Desktop:

  1. Finish Step 8 first so your local main is current and you have no uncommitted edits.
  2. Choose Current Branch → sam-design. Check that the top says sam-design.
  3. Click Current Branch → Choose a branch to merge into sam-design.
  4. Select main, then click Merge main into sam-design.
  5. If Desktop says the branch is already up to date, there is nothing new to merge. Otherwise, let the merge finish. If a conflict appears, keep both people’s work and ask your instructor for help deciding what to change.
  6. Return to IntelliJ. Check that both changes are present and run the app. Fix any problems on sam-design, then save and commit those fixes.
  7. Click Push origin in Desktop. The merge is saved in Git automatically; code fixes need their own commit. If your PR is already open, it updates when you push.

Check the direction: main → sam-design adds the team’s work to Sam’s branch. It does not put Sam’s work into main. That happens through Sam’s PR.

D. Review the next PR and repeat

Review and merge Sam’s PR. Everyone follows Step 8 again to get the combined main. Repeat Step 9C for the next unfinished branch, then review its PR. Handle one PR at a time.

Different files usually make merging easier, but the combined code still needs testing. Check that the app runs after each merge. Keep each student’s merged PR URL for your milestone submission.

If something looks wrong

  • You cannot clone or push: check the team URL, accepted invitation, and signed-in account. Ask the lead to check your access. Do not make a replacement repository.
  • Your edits are missing: save in IntelliJ and check that IntelliJ’s folder matches Desktop’s Show in Finder/Explorer folder. Also check Current Branch.
  • Your branch is missing on a teammate’s computer: publish/push your branch; your teammate then clicks Fetch origin.
  • Lots of generated files appear: check that the supplied .gitignore is present. If those files were already committed, ask for help; adding an ignore rule does not remove them from Git history.
  • JavaFX will not launch: use the Maven goal clean javafx:run, check JDK 21, and share the exact error with your instructor.
  • Desktop will not let you switch, pull, or merge: keep your work and ask for help. Do not discard files, force-push, or delete .git to fix it.

A few words you will see

  • Clone: make your first local copy of the team repository.
  • Branch: your own line of work within that repository.
  • Commit: save a snapshot in Git on your computer.
  • Push: upload your commits to GitHub.
  • Pull request: ask for review before merging your branch.
  • Merge: combine changes from two branches.
  • Fetch: check/download GitHub’s history without changing your working files.
  • Pull: bring GitHub’s changes into the branch you have selected locally.
