Milestone 3: Final Project Specification

Your project may be a game, solver, simulation, utility, or another interactive application.

Must-have features: the baseline application

  • A working JavaFX GUI with graphics or a designed layout. The submitted project launches with usable controls and a visible result. Show JavaFX visual work: a game board or sprites, an interactive map, or a solver layout with clearly grouped inputs, controls, and results. A console program or unchanged starter window does not meet this requirement.
  • Meaningful user interaction. A user action runs your project’s actual logic. Buttons, mouse clicks, text entry, and keyboard input are options; use the controls that fit your application.
  • Meaningful application state. The app remembers data that matters to its task, and later actions use or change that data. Examples include a board, collected items, current problem, result, or session history. The display agrees with the data.
  • One complete workflow. A user can begin a task, perform connected actions, and reach a useful outcome. The result must come from the user’s actions and your logic.

A window alone is not a complete project. A renamed Drone Arena with moving graphics, but no working project rules or outcome, shows partial progress. Likewise, a solver screen with text fields and a fixed answer has no complete solving workflow. Partial work receives credit for the implemented behavior, working connections, and design you can demonstrate; identify what works and what remains incomplete.

What you need for 100%

Complete the baseline and every requirement below. Use the project examples to see how levels, progress displays, and screens apply to your application.

  1. Build a complete screen flow. Include a welcome/instructions screen, the main game or application screen, and a game-over/results/summary screen. Provide working controls to start, navigate, and play or use the app again. You may switch JavaFX scenes or replace content within one window.
  2. Add levels or staged content. Provide at least two playable levels, quiz rounds, map challenges, or supported solver problem types. The second must change the content, rules, difficulty, or calculation; changing only the title or background is insufficient. Show which level, round, challenge, or problem type is active.
  3. Display score, progress, or results. Keep a visible display that updates from the model as the user acts: score and level for an arcade game, correct answers and question progress for a quiz, completed locations for a map activity, or the current problem and computed result for a solver. Show the final outcome on the results screen.
  4. Finish the graphics and layout. Arcade games must use image sprites for the player and relevant game objects rather than only placeholder rectangles or circles. A quiz needs clearly arranged questions, answer choices, and feedback. A campus map needs a visible map with selectable locations and clear selection feedback. A solver needs aligned, labeled inputs and readable results. Include required image files in the repository and credit their sources.
  5. Make the application readable during the demo. Test the app at the size you will present. Enlarge the window and fonts so the audience can read instructions, controls, scores, and results. Nothing essential may be clipped, overlap, or require the audience to read tiny text. Check this before presenting.
  6. Complete and connect the core mechanics. Every core feature listed in your team document works in the combined app. For example, collisions update score once, quiz answers update progress once, map selections show the correct location information, and solver inputs produce computed answers. Discuss changes to the agreed core with the instructor.
  7. Handle errors and reset correctly. Check an invalid action or input, a boundary or special case, and another complete use. Give helpful feedback and preserve valid state. Restart must reset the appropriate score, round, selected location, inputs, and results. For timed games, stop updates at game over and avoid duplicate timers after restarting.
  8. Show the Java objects behind the interface. Keep rules, calculations, and application data in model objects rather than putting the whole program in screen setup or button handlers. Update your UML. During the demo, identify the responsible classes and trace one user action from the control to the model and back to the display.
  9. Record concrete correctness checks. In your team document, show input/action, expected result, actual result, and fix/retest for a normal workflow, an invalid action or boundary, and restart/repeated use. Check both levels, rounds, challenges, or problem types. Use known answers for calculations. Manual checks are acceptable.
  10. Finish the code and project record. Push the final source and resources to GitHub. Include README launch instructions and the final commit identifier. Update the Google Doc with screenshots, current UML or a link to it, test results, challenges, remaining limitations, and individual work logs. Each log records dates, time spent, specific tasks, and links to the related code, commits, or reviewed pull requests. Keep Help Citations and AI learning documentation current under the course policy.
  11. Present the application in class. Give a short sales pitch: who the app is for, what it does, and why someone would use or play it. Run the app and walk through its game mechanics or application workflow, including screen transitions, levels/content, score or results, and restart. Each teammate identifies their contribution and can explain their code. No slides needed.

Weekly work expectation: each team member must spend at least 6 hours per week working on the project, including in-class project time and outside-class meetings/work. Record actual time and completed tasks in individual work logs.

Before your demo and final report

Milestone 3 totals 100 points: Final Project Demo (60) and Final Project Report (40). Use the Milestone 3 Google Doc template in your existing team Google Doc.

  • Run the final JavaFX app from the latest code on GitHub; include every required resource and verify the README launch steps.
  • Update the Google Doc with supported scope, screenshots of the real application, current UML or a link to it, checks and results, challenges, limitations, and each teammate’s work log with evidence links.

  • Rehearse your short sales pitch and live walkthrough in class. Show mechanics/workflow, screen transitions, levels or content, score/results, and restart. Test the window size and fonts for audience readability. No slides needed.

Project goals

The final project is about turning a rough idea into an object-oriented design that can be implemented in Java. In the early milestones, your team should focus on a clear user, a small runnable interaction, and an understandable class structure.

Later milestones will build on this foundation with more features, testing, and polish.
